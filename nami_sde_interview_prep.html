PART 1 — PROJECT MASTER OVERVIEW

1. Problem Statement

Group motorcycle and bicycle riding is inherently dangerous due to rider dispersion, blind turns, sudden traffic/road hazards, and emergency isolation. Riders cannot safely look at their phones while operating a vehicle at high speeds. Existing solutions (like WhatsApp live location or Google Maps sharing) are not built for navigation-speed real-time telemetry, lack low-latency relative proximity indicators, do not support voice-synthesized turn/hazard alerts, and fail when group members fall out of visual line-of-sight.

2. Target Users

  • Motorcycle touring clubs and weekend riding groups.
  • Bicycle peloton groups and cycling commuters.
  • Convoy road-trip travelers needing live telemetry, relative orientation, and immediate crash/SOS dispatch.

3. Why This Problem Matters

Riders traveling at 60–100 km/h cover 16–28 meters every second. In a group, when a tail rider encounters a mechanical failure, takes a wrong turn, or crashes, it can take miles for the front of the pack to realize someone is missing. Nami solves this with real-time distributed telemetry, automatic stopped/gap detection, high-contrast off-screen edge radar, and one-tap emergency SOS broadcast with voice alerts.

4. What Nami Does

Nami is a real-time, low-latency mobile group navigation and telemetry platform. It enables riders to create a ride, instantly invite squad members via cryptographic QR codes or 6-character room codes, stream 1 Hz GPS coordinates + heading + speed + battery level, visualize riders with custom animated map markers, detect off-screen riders via trigonometric edge radar, report road hazards, and broadcast priority emergency SOS alerts synthesized into speech.

5. Main User Journey

  1. Authentication: Sign in via Firebase Auth (Google OAuth or Email/Password).
  2. Dashboard / Lobby: View ride history and quick stats. Create a new ride (selecting destination via Nominatim/Photon geocoding) or Join via QR code scan / 6-character code.
  3. Waiting Lobby: Leader reviews squad list, shares join payload, and transitions ride state from lobby to active.
  4. Active Navigation:
    * Map camera auto-tilts (52° pitch in heading-up mode) with bottom-third projection.
    * Real-time GPS stream (1 Hz) updates rider marker position and heading vector.
    * Off-screen riders projected onto viewport screen perimeter with distance and arrow icons.
    * Voice synthesis announces turns, distance remaining, and incoming hazard alerts.
    * Hazard reporting (Pothole, Police, Traffic, Accident, Animal, Weather).
    * Emergency SOS button broadcasts high-priority distress status with audio/haptic escalation.
  5. Ride Completion: Leader or individual ends ride; stats (distance, duration, top speed, average speed) are computed, saved to local AsyncStorage and Firestore, and presented in RideSummaryScreen.

6. Most Important Features

  • Sub-second Telemetry Streaming: 1 Hz GPS updates with battery and speed telemetry.
  • Trigonometric Edge Radar: Off-screen rider projection using atan2 angle calculations and Haversine distance.
  • Cryptographic QR Join: JSON payload with join tokens, debounced against camera multi-frame race conditions.
  • Multi-tiered Resilient History: Dual persistence in local AsyncStorage (0ms offline retrieval) and Cloud Firestore.
  • Automated Audio HUD: Text-to-Speech synthesis for navigation instructions and squad alerts.

7. Technology Stack

  • Frontend: React Native 0.81.5, Expo SDK 54, TypeScript.
  • Maps & Geospatial: react-native-maps (Google Maps provider on Android), CARTO tile layer, Open Source Routing Machine (OSRM) REST API, OpenRouteService API (fallback).
  • Geocoding & Weather: Komoot Photon API / OpenStreetMap Nominatim, Open-Meteo Weather API.
  • Backend & Database: Firebase Authentication, Google Cloud Firestore (NoSQL, real-time WebSocket listeners).
  • Hardware & Native: expo-location, expo-sensors (Compass magnetometer), expo-battery, expo-speech, expo-secure-store, Android Native CMake/C++ JNI.

9. Why This Project is Technically Interesting

  • Mobile-Hardware Integration: Real-time fusion of GPS location provider, compass magnetometer readings, battery state, and audio synthesis pipelines under constrained CPU/battery budgets.
  • Geospatial & Viewport Trigonometry: Transforming global spherical coordinates (WGS84 Lat/Lng) into 2D screen coordinate bounding boxes with angle calculations (Math.atan2) and elliptical border clamping.
  • Distributed State Synchronization: Handling $N$ riders writing to subcollections at 1 Hz, avoiding $O(N^2)$ document lock contention while maintaining real-time reactive UI at 60 FPS.

10. Biggest Engineering Challenges

  • Firestore Document Contention: Migrated from a single monolithic ride document to independent /locations/{userId} subcollections to avoid lock conflicts at 1 Hz update frequencies.
  • Camera Multi-Frame Scan Race Conditions: Resolved rapid duplicate QR code callbacks using an atomic scan lock ref with debouncing.
  • Android Native Canvas Marker Clipping: Fixed hardware bitmap rendering bugs in react-native-maps by enforcing explicit coordinate anchors, fixed layout bounds, and transient tracksViewChanges state toggles.

From an architectural standpoint, the frontend is built on React Native and Expo with TypeScript, using a decoupled service-layer pattern. Real-time telemetry presented a classic distributed state challenge: if 10 riders write their GPS coordinates to a single shared ride document every second, you hit Firestore's 1 write/sec document limit and trigger write contention. On the client side, I built a dual-tier storage strategy using AsyncStorage and Firestore rules to ensure zero-millisecond ride history retrieval even in offline or weak-cellular environments. For group joining, I implemented a cryptographically salted QR payload system with atomic scan locking to eliminate multi-frame camera race conditions. The result is a rock-solid, production-ready system that delivers 60 FPS UI performance while processing 1 Hz telemetry streams."

Architectural Layer Breakdown

  1. Presentation Layer (src/screens/, src/components/):
    * Pure declarative React components utilizing custom themes (useTheme) supporting high-contrast Dark and Light navigation palettes.
    * AnimatedRiderMarker: Uses Marker.Animated with custom SVG/vector avatars, heading indicators, and dynamic tracksViewChanges state toggles to prevent Android canvas redraw bottlenecks.
    * BikerRadarEdgeIndicator: Canvas overlay rendering off-screen rider badges on viewport perimeters.

  2. State & Hooks Layer (src/hooks/, src/context/):
    * AuthContext.tsx: Wraps Firebase onAuthStateChanged into React Context, handling session hydration from @react-native-async-storage/async-storage and expo-secure-store.
    * useRide.ts: Encapsulates ride session lifecycle, subscribing to the ride document and managing lobby vs active vs completed state machines.
    * useRiderLocations.ts: Listens to the /rides/{rideId}/locations subcollection using Firestore onSnapshot, maintaining an active in-memory dictionary of rider coordinates.
    * useCompass.ts: Subscribes to expo-sensors Magnetometer at 50ms intervals, applying low-pass filtering to calculate smooth orientation angles.

  3. Service Layer (src/services/):
    * Stateless singleton services encapsulating all business logic, data sanitization, network requests, and hardware API bindings.
    * No direct Firestore calls are allowed inside React components; everything flows through services (RideService, LocationService, NavigationService, etc.).

  4. Utility Layer (src/utils/):
    * firestoreSanitizer.ts: Deep object sanitization recursively removing undefined values before Firestore serialization.
    * qrCodeGenerator.ts: Generates and parses cryptographically salted NAMI:{...} and legacy BIKERRADAR:{...} payload envelopes.
    * haversineDistance(): Great-circle distance calculations between coordinate pairs.

Why Subcollections /rides/{rideId}/locations/{userId} vs Single Document?

Architectural Dimension Storing all locations in /rides/{rideId} Subcollection /rides/{rideId}/locations/{userId} (Nami)
Write Contention ❌ High Collision: Firestore limits writes to a single document to ~1 write/sec. With 10 riders updating at 1 Hz (10 writes/sec), 90% of writes fail or get queued. ✅ Zero Contention: Each rider writes to their own document concurrently. Scalable to $N$ riders.
Payload Size & Bandwidth ❌ Heavy Overload: Every 1 Hz update sends the entire array of all riders' locations over the wire. Bandwidth scales quadratically $O(N^2)$. ✅ Minimal Bandwidth: Each write is ~200 bytes containing only that specific rider's telemetry.
Security Granularity ❌ Weak: Security rules cannot restrict a user to only editing their own index in a root document array without complex array validation expressions. ✅ Strict: allow update: if request.auth.uid == userId enforces absolute document-level ownership.
Atomic Updates ❌ Race Conditions: Two riders writing simultaneously overwrite each other's location unless using transactions (which would fail at 1 Hz). ✅ Isolated: Independent documents eliminate write race conditions entirely.

Firestore Consistency, Real-Time Listeners & Offline Behavior

  • Concurrency & Consistency: Firestore uses strong consistency for single-document reads/writes and multi-document transactions. Because each rider writes strictly to their own /locations/{userId} document, concurrent writes never collide.
  • onSnapshot() Internals: Establishes a persistent bidirectional gRPC/WebSocket streaming channel. Listeners fire immediately on initial attachment with cached/server data, and trigger whenever any document within the matched query/collection changes.
  • Network Drops & Offline Behavior:
  • Firestore maintains an internal in-memory offline queue for pending writes.
  • In Nami, we also implemented an explicit application-level local cache using @react-native-async-storage/async-storage for ride history, ensuring instant 0ms retrieval and offline resilience even if the Firebase SDK cache is cleared.

PART 5 — FIRESTORE SECURITY

Security Rules Architecture & The "Test Mode" Post-Mortem

  1. What Security Rules Are: Server-side declarative authorization rules executed by Google Cloud before any document read or write is permitted.
  2. Why Test Mode Expired: Firebase projects created in "Test Mode" default to allow read, write: if request.time < timestamp.date(YYYY, MM, DD); (a 30-day countdown). On August 15, 2026, the timestamp expired, locking all client access and throwing Missing or insufficient permissions.
  3. The Solution: Hardened production security rules were deployed in firestore.rules, enforcing strict authentication and document-level ownership.

Authentication vs Authorization

  • Authentication (AuthN): "Who are you?" Handled by Firebase Auth via cryptographically signed JSON Web Tokens (JWT).
  • Authorization (AuthZ): "What are you allowed to do?" Enforced in Firestore Security Rules by verifying request.auth.uid against document parameters (userId, leaderId, memberUids).

Security Analysis of Nami Rules

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // 1. User Profiles & Subcollections
    match /users/{userId} {
      allow read: if request.auth != null;
      allow create, update, delete: if request.auth != null && request.auth.uid == userId;

      match /ride_history/{historyId} {
        allow read: if request.auth != null && (request.auth.uid == userId || request.auth.uid in resource.data.memberUids);
        allow create, update: if request.auth != null;
        allow delete: if request.auth != null && (request.auth.uid == userId || request.auth.uid in resource.data.memberUids);
      }
    }

    // 2. Rides & Telemetry Subcollections
    match /rides/{rideId} {
      allow read: if request.auth != null;
      allow create: if request.auth != null && request.resource.data.leaderId == request.auth.uid;
      allow update: if request.auth != null && (
        resource.data.leaderId == request.auth.uid ||
        request.auth.uid in resource.data.memberUids ||
        request.auth.uid in request.resource.data.memberUids
      );
      allow delete: if request.auth != null && resource.data.leaderId == request.auth.uid;

      match /locations/{userId} {
        allow read: if request.auth != null;
        allow create, update: if request.auth != null && request.auth.uid == userId;
        allow delete: if request.auth != null && (
          request.auth.uid == userId ||
          get(/databases/$(database)/documents/rides/$(rideId)).data.leaderId == request.auth.uid
        );
      }

      match /hazards/{hazardId} {
        allow read: if request.auth != null;
        allow create: if request.auth != null && request.resource.data.reportedBy == request.auth.uid;
        allow update, delete: if request.auth != null && (
          resource.data.reportedBy == request.auth.uid ||
          get(/databases/$(database)/documents/rides/$(rideId)).data.leaderId == request.auth.uid
        );
      }
    }

    // 3. Completed Rides & Master History
    match /completed_rides/{rideId} {
      allow read: if request.auth != null;
      allow create, update: if request.auth != null;
      allow delete: if request.auth != null && resource.data.leaderId == request.auth.uid;
    }

    match /ride_history/{historyId} {
      allow read: if request.auth != null && (request.auth.uid in resource.data.memberUids || resource.data.memberUids == null);
      allow create: if request.auth != null;
      allow update, delete: if request.auth != null && request.auth.uid in resource.data.memberUids;
    }
  }
}

Potential Weakness & Production Improvement:

  • Current rule: /rides/{rideId} allows any authenticated user to read active rides. This is necessary for room code discovery (where('roomCode', '==', code)).
  • Production improvement: Use Firestore Hash/Index lookup or Cloud Functions to join rides so private rides cannot be enumerated.

PART 6 — REAL-TIME LOCATION SYSTEM

Telemetry Pipeline

  • Library: expo-location
  • Configuration: Location.Accuracy.High, timeInterval: 1000 (1 second), distanceInterval: 1 (1 meter threshold).

PART 7 — MAP & GEO-SPATIAL MATHEMATICS

1. The Haversine Formula (Whiteboard Derivation)

Calculates the great-circle distance between two points on a sphere given their longitudes and latitudes:

$$\Delta\text{lat} = \text{lat}_2 - \text{lat}_1, \quad \Delta\text{lon} = \text{lon}_2 - \text{lon}_1$$

$$a = \sin^2\left(\frac{\Delta\text{lat}}{2}\right) + \cos(\text{lat}_1) \cdot \cos(\text{lat}_2) \cdot \sin^2\left(\frac{\Delta\text{lon}}{2}\right)$$

$$c = 2 \cdot \text{atan2}\left(\sqrt{a}, \sqrt{1-a}\right)$$

$$d = R \cdot c \quad (\text{where } R = 6,371,000 \text{ meters})$$

In Nami (src/utils/index.ts): Used to compute distance remaining to destination and relative distances to squad riders.

  1. Viewport Bounding Check:
    $$\text{isOffScreen} = (\text{lat} < \text{minLat} \lor \text{lat} > \text{maxLat} \lor \text{lng} < \text{minLng} \lor \text{lng} > \text{maxLng})$$
  2. Relative Offset & Polar Angle:
    $$d\text{Lat} = \text{rider.lat} - \text{mapRegion.lat}, \quad d\text{Lng} = \text{rider.lng} - \text{mapRegion.lng}$$
    $$\theta = \text{atan2}(d\text{Lat}, d\text{Lng}) \quad [-\pi \text{ to } +\pi]$$
  3. Screen Boundary Elliptical Projection:
    $$\text{edgeX} = \text{centerX} + \cos(\theta) \cdot \text{halfWidth}$$
    $$\text{edgeY} = \text{centerY} - \sin(\theta) \cdot \text{halfHeight} \quad (\text{Y is inverted in screen space})$$
  4. Boundary Clamping:
    $$\text{edgeX} = \max(\text{leftMargin}, \min(\text{rightMargin}, \text{edgeX}))$$
    $$\text{edgeY} = \max(\text{topMargin}, \min(\text{bottomMargin}, \text{edgeY}))$$
  5. Directional Arrow Mapping:
    Octant angle $\phi = (\theta \cdot \frac{180}{\pi} + 360) \pmod{360}$ maps to 8 directional icons (arrow-up, arrow-up-right, etc.).

PART 8 — QR SYSTEM & CONCURRENCY CONTROLS

QR Payload Format

NAMI:{"version":1,"rideId":"abc123xyz","roomCode":"K8M2P9","leaderId":"user456","joinToken":"7k2x9a-l0z1m8","createdAt":1724145000000}

The Camera Multi-Frame Race Condition

  • Problem: Mobile camera scanners fire onBarcodeScanned at 30–60 FPS. When a user points the camera at a QR code, the callback executes 10–15 times within 250 milliseconds before the first network navigation completes. This triggered 10 concurrent joinRide() requests, causing Firestore write collisions and screen navigation flicker.
  • Solution: Implemented an atomic useRef<boolean>(false) lock combined with an immediate debounced timeout:
    ts const isScanningRef = useRef(false); const handleBarcodeScanned = async ({ data }) => { if (isScanningRef.current) return; isScanningRef.current = true; try { await processJoinPayload(data); } finally { setTimeout(() => { isScanningRef.current = false; }, 2000); } };

Backwards Compatibility

The parser (parseNamiQRPayload) transparently supports both NAMI: and legacy BIKERRADAR: prefixes, raw 6-character room codes, and deep links (https://nami.app/join/CODE), ensuring older versions of the app can join sessions seamlessly.

PART 9 — SOS EMERGENCY SYSTEM

Architecture

  1. User holds SOS button for 1.5 seconds to prevent accidental triggers.
  2. LocationService.broadcastEmergencySOS updates /rides/{rideId}/locations/{userId} with riderStatus: 'sos'.
  3. An exponential backoff loop executes up to 3 retry attempts on weak network connections.
  4. Remote clients listening via onSnapshot trigger EmergencyAlertOverlay, initiate a haptic vibration loop (Vibration.vibrate([0, 500, 200, 500], true)), and synthesize voice alerts via SpeechService.

Safety-Critical Critique: Is Firestore suitable for mission-critical SOS?

  • Honest Engineering Answer: No, standard Cloud Firestore over consumer cellular connections is not sufficient for life-critical automotive emergency systems.
  • Why: Firestore relies on TCP/HTTPS/WebSockets over public cellular towers, which suffer from coverage dead zones in mountain passes and high-speed packet drop.
  • Production Architecture for Safety-Critical Systems:
  • Fallback to direct SMS / Satellite Emergency API (e.g. Iridium/Garmin inReach or Apple Satellite SOS) sending compact binary GPS coordinates.
  • Cellular UDP binary packets via dedicated edge brokers with dead-man switch heartbeats (if heartbeats cease for >60s while speed was >50 km/h, trigger crash alert automatically).

PART 11 — BATTERY MONITORING

  • Library: expo-battery
  • Implementation: LocationService checks Battery.isAvailableAsync() and attaches Battery.getBatteryLevelAsync() (0–100%) to each 1 Hz location telemetry packet.

PART 15 — IMPORTANT BUGS WE SOLVED (POST-MORTEMS)

Bug 1: Firestore "Unsupported Field Value: undefined" Crashes

  • Problem: Firestore SDK throws unhandled fatal exceptions if any key in an object has a value of undefined.
  • Root Cause: Optional fields in rider telemetry (e.g. battery, photoURL, heading) were evaluated as undefined on some devices.
  • Solution: Engineered sanitizeForFirestore<T>() in src/utils/firestoreSanitizer.ts, which recursively traverses objects and strips or converts undefined to null.

Bug 2: QR Scanner Rapid Multi-Fire Duplicate Joins

  • Problem: Scanning a QR code triggered the join request 10+ times within 250ms.
  • Root Cause: Camera frame processors run at 30 FPS and invoke onBarcodeScanned continuously while the QR code is in view.
  • Solution: Implemented an atomic ref lock (isScanningRef.current = true) with an immediate 2000ms debounce cooldown.

Bug 3: Android Native Canvas Marker Clipping & Grey Square Box

  • Problem: User location marker rendered as a clipped, partial grey rectangle on Android devices.
  • Root Cause: react-native-maps on Android takes a hardware snapshot of marker views. Continuous CSS animations scaling outside the layout boundary caused the canvas bitmap renderer to clip to the view bounding box and draw a grey background.
  • Solution: Replaced unbounded scaling animations with a fixed-dimension transparent container (100x100), applied direct borderRadius to the <Image> component, and set dynamic tracksViewChanges state toggles that settle to false after 600ms.

Bug 4: Expired Firestore Security Rules

  • Problem: All client writes failed with Missing or insufficient permissions.
  • Root Cause: Firestore was initialized in 30-day Test Mode which expired on August 15, 2026.
  • Solution: Deployed production-grade, ownership-verified security rules covering /rides, /locations, /users/{userId}/ride_history, and /completed_rides.
